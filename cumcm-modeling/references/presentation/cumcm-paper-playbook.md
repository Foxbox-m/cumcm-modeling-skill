# CUMCM 普通论文执行主手册

本文件是普通论文生成的唯一执行主来源。它把题面约束、模型证据、正文表达和 G2→G3 交付串成一条链；`paper-depth-and-structure.md` 只做深度诊断，`award-paper-layout.md` 只补版式实现，`cumcm-paper-priors.md` 只提供有边界的离线观察。

## 1. Profile 与证据边界

按任务比例使用本手册：第 1—4 节服务普通论文起草；最终交付或投稿时才启用 G3、复现、提交与视觉审计材料。短任务只读取相关小节，不把完整终检流程当作普通写作前置条件。

写作前按以下顺序解析题面/用户交付要求、`problem_source` 与 `submission_profile`。前者只描述题目来源（`CUMCM|MCM|custom`），后者决定语言、版式、页数和审计（`CUMCM|MCM_NATIVE|research_report`）。无明确要求且执行 CUMCM 交付时才默认 `CUMCM`；`MCM_NATIVE` 完全服从题面/官方原生要求。

把题面与赛区交付约束、当届官方硬项和 Skill 内部质量建议分开。项目启动先读取题面、附件及当届 `L0` 硬交付摘要；CUMCM 论文写作前复核 `competition-rules` 的硬边界，`G3` 再完整读取规则层 `R`。历史论文只作校准或反例，不是规则、奖级配额或模型白名单。普通候选先独立推导；数学原语与模型卡只在结构识别后按需读取；历史方法台账仅在来源追溯、历史失败案例或方案比较时按需读取。表现先验只在已有独立模型与结果的论文写作/表现校准阶段读取。

## 2. Schema 4 任务交付契约

完整整题、最终论文或完整结果包的 `modeling-brief.md` 使用 Schema 4，无论交互轮次多少。持久化内容只保存 profile 信息，以及每个实际任务的 `deliverable`、`model`、`why`、`validation`、`answer`；运行细节归 `results/reproducibility.json`，引用归 `citation-ledger.md`，两者仍是各自的单一事实源。简报任务块用 `### Q1`…稳定任务 ID；题面无显式编号时，在 `deliverable`/`why` 中说明该 ID 到论文语义标题的映射。下方是唯一字段示例：

```text
brief_schema_version: 4
problem_source: CUMCM
submission_profile: CUMCM
profile_basis: <题面、用户要求与适用规则的来源>
current_gate: G1

## 任务证据

### Q1
deliverable: <本任务的直接交付物>
model: <独立识别结构后的数学表示与输入输出>
why: <选择该表示、基线和关键假设的理由>
validation:
  plan: <G1 的验证计划>
  evidence: <G2/G3 起填写项目内相对路径；G1 可暂缺>
  finding: <G2/G3 起填写验证发现；G1 可暂缺>
answer: <G2/G3 起填写正式答案；G1 可暂缺>
```

命令接口保持统一：

```bash
python3 <SKILL_ROOT>/scripts/check_project_brief.py <PROJECT_ROOT>/modeling-brief.md \
  --require-profile-contract --require-schema 4 --require-gate G1
```

仅当题面显式编号且已确认有 N 道任务时，才在上述命令追加 `--expected-questions N`；N 为正整数，任务顺序不限。题面没有显式编号时省略该参数，checker 不从现有 ID 推断集合。profile 信息与任务证据是简报的最小交付接口，不应复制运行结果、引用状态或正文页数事实。G1 只需填写 `validation.plan`；G2/G3 还需填写项目内相对路径形式的 `validation.evidence`、`validation.finding` 和 `answer`。作者仍需在工作过程中检查输入、约束、关系来源、参数/假设/单位、求解、机制、局部风险、跨任务接口和直接答案；这些是风险审查清单，不要求持久化为额外任务字段。

已确认题面存在显式问题数 N 后，先生成可见论文骨架，再填入题目化标题和正文内容：

```bash
python3 <SKILL_ROOT>/scripts/build/generate_paper_scaffold.py \
  --profile cumcm --questions N --format tex --output <PROJECT_ROOT>/paper/main.tex
python3 <SKILL_ROOT>/scripts/build/generate_paper_scaffold.py \
  --profile cumcm --questions N --format docx --output <PROJECT_ROOT>/paper/main.docx
```

其中 `N` 必须来自题面已确认的显式编号；无显式题号时不得臆造 N，沿用语义任务映射并人工调整骨架。正式论文仍须替换/删除模板占位符，不能把脚手架生成成功当成内容或提交放行。

## 3. CUMCM 默认模板与 Functional Coverage Contract

CUMCM 默认从以下七章脚手架起稿；它是高可用模板，不是官网规定，也不是普通 `--award-style-audit` 的固定章数硬门。题面、用户模板或论证需要时，可以合并、拆分或按问题/模型组织，只要 Functional Coverage Contract 和提交材料不丢失；只有明确要求精确七章时才使用 `--strict-structure`：

1. `一、问题重述`：固定含 `1.1 问题背景` 与 `1.2 问题要求`；背景短写，要求按题面逐问改写，不提前泄露模型答案。
2. `二、问题分析`：固定按 `2.1`—`2.N` 逐问展开。每问说明题目对象与输出、结构困难、实际传递的数学量/方程/约束、拟采用的数学表示或求解路线及验证出口；不能只列算法名，也不把内部任务路由写成论文叙事。
3. `三、模型假设`：集中列出全局共享且会影响模型成立性的假设；局部假设仍在首次使用处解释其影响。
4. `四、符号说明`：只放“符号—含义—单位”三列表；局部临时量仍在公式后解释，不能把符号表写成模型准备章。
5. `五、模型的建立与求解`：固定按 `5.1`—`5.N` 对应题面各问。每问内部标题由本题生成，功能上完成模型/表示、推导与求解、正式结果、机制解释和局部证据；共享模型可置于第五章开头，但不得另起“模型准备”一级章。
6. `六、模型的分析与检验`：只汇总跨问题、系统级或共同风险的检验，二级结构按实际方法命名；逐问局部验证仍紧邻第五章相应结果，不能被本章替代。本章不得回顾软件架构、运行组织或全文工作流。
7. `七、模型的评价`：固定含 `7.1 模型的优点`、`7.2 模型的缺点与改进`，评价必须指向已展示的结构、结果和验证证据。
8. `参考文献` 与 `附录` 使用未编号标题。附录先按问题顺序列完整代码，再列共享模块、运行说明和支撑材料清单。

Functional Coverage Contract 要求可定位地覆盖：题目理解与任务映射；必要假设与符号（可合并或在首次依赖处定义）；模型推导与求解；正式结果与现象/机理解释；决定性验证；局限/评价；参考文献；附录完整代码与材料清单。它不新增 Schema 字段。默认模板不另设“结论”一级章，每问末尾直接作答，摘要承担全局结论压缩；其他结构也须提供功能等价的作答出口。AI 工具使用声明只有在当届规则要求时才按指定位置加入，不作为编号叙事章节；当前 2026 规则要求所有参赛队在参考文献之前声明，未来届次必须重新核验。`MCM_NATIVE` 与 `research_report` 完全按各自 profile 组织，不套用本模板。

主模型进入求解前，作者应回答：结构困难是什么；关键关系来自题面、守恒/几何/统计假设、数据估计还是外部来源；相对适用的 baseline 或其他参照增加的机制或约束为何必要；参数、边界和初值如何获得且在适用时是否可辨识；哪些量主导结果、用什么局部证据验证。模型卡和数学原语只在独立识别结构后按需调用。

Layer B 的 Part B Narrative Bridges 在模型正式冻结前不可读取；冻结后也只读取实际使用 Pattern 对应的 bridge。正文必须从当前题对象、关系和现象重写该 bridge，bridge 只能帮助解释或触发必要图件，不能反向决定模型结构。

### 3.1 统一逻辑跨越与自适应论证

每个主要论证都应能跨越“现实 → 数学 → 可计算 → 求解 → 结论 → 可信”这条统一逻辑链：先说明对象、任务和事实，再给出关系与假设，明确如何计算和求解，报告正式结果，最后用与风险匹配的证据说明可信范围。这是内部组织义务，不是固定章节、字母标签或段落顺序。论证顺序按主导结构自适应选择：

- 几何/机理题可从对象与机制图、坐标和关系出发，再到方程、离散或数值求解、结果与守恒/边界验证；
- 优化/决策题可从现实决策动作及其状态/成本后果出发，再到决策变量、目标、约束/可行域、结构利用、求解与方案的敏感性/稳定性验证；
- 数据/统计题可从数据生成与质量、目标和切分出发，再到特征/模型、估计或预测、误差与不确定性验证。

混合题可组合这些顺序；简单题可省略不适用环节。多问在内部计划中先判断 Cascade/Parallel/Hybrid，再决定哪些数学对象需要前置、哪些任务独立展开；该路由标签不进入最终问题分析或正文，不为形式上的逐问一致而重复公共内容。

按需发现链接：只有在已有独立模型和正式结果、且遇到具体写作或图件认知瓶颈时，才读取 `../evidence/recent-writing-visual-distillation.md` 的相关卡片；遇到工程元叙事、机械同构或竞赛语态问题时，才读取 [`competition-paper-voice-distillation.md`](../evidence/competition-paper-voice-distillation.md)。运行层只消费跨样本综合卡及其抽象决策条件，不消费具名论文的章节、措辞、图式或题解；当前题不满足适用条件时 abstain。这些受限证据不默认全读，也不作为题解模板或规则。

提纲反模板：使用默认七章模板时，第五章各问的二、三级标题必须由本题证据、共享关系和题号映射生成；使用其他结构时，在语义任务区间完成同样闭环。不得把“现实 → 数学 → 可计算 → 求解 → 结论 → 可信”或自适应链名直接当作目录，也不得要求每问套用同一组内部子标题或同一顺序。证据相邻环节可以合并，但题号/语义任务映射、结果、验证和直接答案必须可定位。

### 3.2 逐问展开与题目化标题

“逐问”是题面任务映射，不是把同一套套话复制 N 次。`1.2 问题要求` 应按题面动作逐项改写并给出可核对的输出；每个 `2.i` 的第一自然句必须直接落到第 i 问要解决的对象、动作或输出，随后用本问实际传递的变量、状态、方程或约束说明困难、模型路线和验证出口。`5.i` 同样必须以本问的模型对象或待求量起笔。

非简单小问可按模型/表示、求解/结果、解释/验证/作答组织功能层；功能层可以合并或拆分，但标题必须题目化（对象、机制、决策、指标或验证动作），不能机械使用“模型建立/模型求解/模型检验”等空泛标题；简单任务允许合并为一个可读的题目化小节，只要模型、结果和答案仍可定位。

使用默认七章模板时，`5.i.3`（或本问对应的末层）负责本问结果的解释、局部证据与直接答案，第六章只负责跨问题、系统级或共同风险的综合分析与检验；使用其他结构时，相应内容在本问语义区间和跨问检验区间完成。任何结构都不得让综合检验吞掉某一问唯一的局部验证，也不得重复整套跨问检验。

### 3.3 多问关系路由

多问先在内部计划中判断 `Cascade`、`Parallel` 或 `Hybrid`，不新增 Schema 字段，也不把这些标签写进问题分析或正文。只有真实级联时，内部计划才记录前问传来的对象、前问表示为何不足以及本问增加的变量、约束、求解或验证；并列任务直接写各自的对象、数据/场景、困难、表示和验证出口；混合任务只写真实存在的共享核心与接口。最终论文把上述关系还原为实际传递的数学对象、方程和约束，自然体现继承或独立性，不出现“混合路由”“分支”“共同接口”“交付动作”等架构元叙事。

## 4. 论证写作单元

每个任务围绕题面动作组织，而非算法名。正文应让读者定位目标/输出、输入与约束、模型、求解或推导、正式结果、主要风险的局部验证和直接答案；局部验证按主导风险选择解析、边界、守恒、可行性、留出/回测、残差、收敛等证据，不机械要求全部类型；跨任务综合检查不能替代局部验证。

公式采用“三明治”：前文交代关系、依据或决策，公式独立承担一个论证动作，后文解释符号、单位、参数来源、假设和如何进入求解。图表采用“问题—证据—读取—边界”：先提出要回答的问题，再给出匹配数据结构，读取趋势、差异、拐点、区间或数值，最后说明结论边界。图型由主张和数据结构决定；纯解析任务可用推导、边界表或情形表替代数据图并说明理由。

### Fast Narrative Lead

新核心模型、非平凡关系或模型升级首次出现前，先给出由认知缺口决定长度的最短充分现象/直觉，随后立即进入机制图、变量、公式或目标约束。禁止长背景、探索日记和失败尝试占据模型入口。

### Result Interpretation Loop

按“结果 → 题目现象/状态 → 主导变量/约束/几何/机理 → 题意”读取正式输出，仅在风险尚未关闭时保留足以关闭主要风险的必要局部验证；若不同主要风险需要不同证据，分别保留。摘要优先写模型与现象；每问只保留一项真正改变评委判断的验证细节。

### One Limitation, One Primary Home + Local Justification

使用默认七章模板时，全局建模假设和整体局限分别集中在第三章与 `7.2`；其他结构设置功能等价的假设与局限位置。公式成立所需的小量、尺度或局部近似始终在首次依赖附近简洁解释。相同免责不在多个章节重复，局部依据也不替代整体局限。

### Analytical Elevation Opportunity

仅当守恒、单调、对称、尺度、界或临界条件能够由现有模型严格推导，且提升为性质/命题有解释或简化价值时才这样写；否则保留为数值观察。不强制 theorem 环境，也不把它当作 Gate 或 KPI。

### 4.1 中文论证执行

一段文字承担一个主要论证动作；逻辑连接由真实的因果、对照或条件决定，不靠套用固定句式。主张强度随证据校准：计算结果可写“得到/显示”，证据关系可写“支持/与……一致”，统计结果区分“关联”与“因果”，只有设计和检验确实支持时才使用“显著”或“推广”，并同时写清边界。“证明”只用于已经给出严格推导/证明的数学命题；仿真、拟合、优化和有限样本结果使用“结果显示/支持/在该情景下得到”，不得用“证明”扩张证据。报告 \(R^2\)、残差或误差时标明样本内、样本外或独立验证口径。摘要和结果段使用真实量化结果及其适用边界，避免“优越”“精准”“充分证明”等空泛结论；不规定固定句式、字数或段落顺序。

### 4.2 一页摘要与论文可见性防火墙

摘要的详细写法、结果精度、逐问锚点、继承对象、关键词和自审方法统一见 [`abstract-writing.md`](abstract-writing.md)。对有显式 Q 道问题的摘要，默认 Q 个逐问段加 1—2 个共同段，通常为 `Q+1 ≤ P ≤ Q+2` 且优先 `Q+1`；每问段以归一化锚点“针对问题 x，”开头，Q+2 只用于真实共享框架或有独立信息价值的跨问综合。无显式问题划分时关闭 Q/P 与锚点规则，按实际任务逻辑组织，不臆造题号。上述是 L1/跨样本写作默认，不是官方规则；不固定内部句式、段长、结果数量或验证配置。

项目治理语言与论文语言严格隔离。`Schema 4`、`G1/G2/G3`、`modeling-brief`、`reproducibility.json`、`claim binding`、`JSON Pointer`、`run role`、`selected_run`、`candidate run`、`事实源`、`运行清单`、`可复现性与交付一致性审计`、`checker`、`paper artifact`、`视觉审计`、`构建流程`、`结果宏`、`manifest` 等只用于内部文件和支撑材料，不得出现在 CUMCM 摘要与正文。由它们保证的数学证据可以进入论文，但必须改写为模型、参数、误差、对照、结果与适用边界。

## 5. 页数、G2 与 G3

页数依据最终实际渲染的 PDF 和 `check_paper.py` 审计，不由简报手填事实。摘要、正文、附录和总页数在渲染后按题面/赛区定义核对；CUMCM 内部页数建议只能作为质量诊断，不能替代官方要求，也不能用水字数、重复图或缩小字体达标。机器门只识别结构信号，不能证明数学质量、结果真实性、图文论证、匿名或视觉完成。

G2 先冻结正式运行、参数、结果、图件来源和关键数值，确认任务—运行输出—图表—正文结论可追溯，更新 `reproducibility.json` 与引用台账，并完成与主导风险匹配的局部验证。图件先通过脚本检查，再在最终插入尺寸下人工查看；不能以文件存在或退出码代替结果核对。

G2 冻结后只做两次写作通过：Phase A 对每个语义任务区间前向生成；使用默认七章模板时对应 `2.N`/`5.N`，一次完成“现象 → 直觉 → 数学 → 求解 → 正式结果 → 现象/机制 → 必要局部验证 → 可定位作答”。这是隐含因果链，不要求各问使用相同标题、相同长度、相同段落数或统一“直接回答：”句式。Phase A 仅在风险尚未关闭时保留足以关闭主要风险的必要局部验证，若不同主要风险需要不同证据，分别保留。Phase B 只做一次全文读取；完整论文或最终交付时，Competition Paper Voice 与 Claim Calibration 不以用户额外点名为前提，但仍仅处理实际观察到的问题；Caveat/限定语也仅处理本次全文扫描发现的问题，所有维度均不机械执行无问题项；局部任务只归类当前任务范围内实际观察到的问题。合并清单后一次局部修复，之后只复验受影响维度；Semantic Emphasis 仅在发现具体语义导航缺口，或最终正式交付确需扫读导航时启用，局部语态/限定语清理不得自动增加或调整粗体。保护公式、label、cite key、图表路径、正式数值、单位、冻结参数、硬约束与 LaTeX 结构；限定语只在重复且不改变结论时压缩。发现事实或数字问题时回到事实源，不在 Phase B 改模型。

### Competition Paper Voice Pass

这是 Phase B 内部的前台—后台语态检查。逐段保留对评委有价值的题面事实、数学对象、推导、求解原则、正式结果、机制解释、必要验证与结论边界；代码架构、数据治理、运行入口、Schema/Gate/QA、调用关系和重复的全篇组织说明，移到内部/支撑材料，或改写为它们实际保证的数学含义。第六章不得借综合检验回顾软件架构；工程 QA 只在后台保证一致性，不作为正文验证。

执行两个保守测试：一是**换语言测试**——把 Python 换成 MATLAB 后句义变化而数学关系不变，该句通常属于实现层；二是**删除测试**——删去一段后数学对象、正式结果、适用边界和答案定位均不受损，该段通常是元叙事或重复组织说明。附录仍按现有契约放置完整可运行源程序，但正文与附录说明不写真值源、Schema、Gate、正式入口、读回审计、调用图等治理说明；只保留竞赛复现确实需要的输入、运行方式和输出文件说明。

词语按语境处理，不得全局禁用“结构、模块、接口、基线、复用”：它们用于真实数学对象、物理界面或模型比较时可以保留；用于解释论文、代码或工作流组织时应改写或移出。baseline 仍是建模证据，正文可依语境写成简化模型、参照模型或初步估计。摘要和逐问收束还要做非机械同构检查：逐问覆盖、量化结论和答案可定位性必须保留，句法、信息密度、篇幅层级和作答措辞则由各问证据决定，不固定验证数量。

### Semantic Emphasis Pass

这是 Phase B 内部的条件式表现子步骤：仅在发现具体语义导航缺口，或最终正式交付确需扫读导航时启用；不改变文字、数值或公式，只增加必要的语义导航。摘要可选择性加粗短任务锚点（如“针对问题一”）和必要的核心模型名；正文只对任务/步骤标签、首次核心模型或决策对象、直接回答标签等短语义单元加粗。不得整段、整句、孤立数字、公式或题注加粗，也不得反复加粗同一术语，不设粗体比例或 KPI。表现校准需要证据时才读取 [`award-paper-bold-distillation.md`](../evidence/award-paper-bold-distillation.md)，且不得复制样本文字、题目答案或把 A1R 展示当作奖级证据。

模型论证与结果区间是正文主体；使用默认七章模板时主要落在第五章。软内容预算优先给模型、推导/求解、正式结果、局部验证和题目化解释；背景复述、通用算法科普、重复图表、过程日志和空泛评价不得挤占主体。预算是写作诊断而非固定页数、字数或图表 KPI：当篇幅不足时先保留每问闭环与证据，当篇幅过长时先删重复和套话。

### Page-Flow/Whitespace Pass

最终交付的页面流、留白修复、浮动策略和最终 PDF 图文核对，按 [`award-paper-layout.md`](award-paper-layout.md)、[`word-workflow.md`](word-workflow.md) 与 [`award-paper-visualization.md`](award-paper-visualization.md) 的详细流程执行；普通正文页默认保持图文叙事邻接，内容区间并集覆盖率低于约 60%或最大内部连续空白高于约 25%，仅作经验定位，需联系表与原尺寸人工复核，不得单独成为官方规则或阻断条件。

进入 G3 后绑定论文源文件、完整附录源文件和支撑材料清单，生成并渲染 PDF/DOCX，运行：

```bash
python3 <SKILL_ROOT>/scripts/check_paper.py <PROJECT_ROOT>/paper/final.pdf \
  --profile cumcm --award-style-audit
```

`--award-style-audit` 是普通终检：审计 Functional Coverage Contract、表现和官方硬项，不固定一级章数量；功能无法从文本层确认时只进入人工检查。只有用户、题面或模板明确要求精确七章时改用 `--strict-structure`，把七章标题与顺序、1.1/1.2、2.1—2.N、5.1—5.N、7.1/7.2、符号表头和未编号参考文献/附录作为 Skill 内部模板门。两种模式都保留内部术语、占位符、正文代码隔离、附录、页面流和官方硬项审计。仅题面显式编号时追加 `--expected-questions Q`；未编号题面省略并人工核对语义映射。

使用默认七章模板时，`7.2 模型的缺点与改进` 先列已暴露的缺点、适用边界或失败条件，再给出对应改进方向及代价/验证计划；其他结构在功能等价的局限/评价区间采用同一顺序。附录只列竞赛可见的提交材料：按题号排列的完整可运行源程序、必要的共享模块/运行说明，以及题面或当届规则要求随论文提交的支撑材料文件清单；调试日志、内部 gate、临时缓存、未提交中间文件和内部治理记录不得冒充附录材料。

最终放行还要求题目—代码—结果—图表—正文一致，支撑材料可复现，当届规则与真实 AI 使用记录闭合。通过机器检查只说明可机械识别项目通过。

### 5.1 写作契约回归

对有明确题号的论文，每个语义任务区间的开头落到本问对象、动作或输出；使用默认七章模板时对应 `2.N` 与 `5.N`。其他结构以“问题一/第一问”等语义标题区间定位模型、求解、结果与局部验证，正文中的偶然提及不能制造额外问题。默认模板的符号章或假设章若职责污染只记 `QUALITY_WARN`；合并结构则按首次依赖与功能覆盖人工判断。

共享核心只有在同时服务至少两问、后续能够直接调用、前置定义能减少重复且不引入单问细节时才前置；使用默认七章模板时可置于第五章开头，否则置于首次共同依赖前。附录逐问先说明本问特异核心函数/签名和主求解逻辑，再在后置共享区完整列出公共代码一次。图件遵循“认知瓶颈 → 图件 → 正文消费”：图件未被正文解释时记录为质量问题；`paper_visuals` 的未消费 native schematic 仅在 `--require-paper-artifacts` 严格模式阻断。

页数、核心论证页和主体稿/附录/总页数都以最终渲染 PDF 分账输出；严格七章模式另输出七章模板跨度，普通 award-style 模式输出可识别语义章节/功能覆盖定位。页数信号只作软提示，不替代题面/官方硬项，也不以固定图数、字数、参考文献数或共享模型页数达标。附录题号到入口映射仍是硬契约；仅有文件名而没有可见的本问特异函数/控制逻辑时只提示人工复核。
